---
name: visual-review
description: Present interactive HTML plans before implementation, actual results after implementation, and code or PR reviews with source-bound checkpoints. Use for substantive implementation, planning and review tasks; ordinary discussion and inspection need no visual.
---

Use this companion's `scripts/visual-review` CLI. Resolve its absolute path relative to this skill's plugin root. Pass `--cwd` and the exact host `--session` reported by the hook repair command. Do not guess a session or share another agent's task scope. Hooks for some subagents use the parent's session; delegated readers must leave the parent's task alone.

Run `status` first. Declare a substantive task with `begin --kind implementation|plan|code-review|pr-review --scope "the requested outcome"`. Reviews require `--base COMMIT --target COMMIT`. If discovery is needed, declare `--pending`, inspect the source, then `resolve --base COMMIT --target COMMIT`. Git refs resolve again at each check. Explicit new scope requires `begin` with the new scope; use `--new` for a new task with the same scope. Ordinary followups keep the active task and valid plan. Do not change an unfinished implementation to discussion to bypass its final checkpoint.

Read the bundled upstream [SKILL.md](../../vendor/visual-explainer/SKILL.md) only when producing a visual, then the specific template/reference it selects. The upstream files are unchanged at the pinned revision. Ignore upstream installation or MCP setup directions here; use the bundled dependency-free renderer through this companion.

Author a substantive interactive `<stage>.src.html` under the external artifact path returned by `status`. For plans, show the actual proposed behavior, scope, decisions and verification. For postimplementation, inspect the real diff and show the resulting behavior, validation and remaining limits. For reviews, inspect the explicit base/target diff and show actionable findings with evidence. Use upstream interaction conventions, accessible diagrams, expandable details and relevant choices. Do not substitute a status dashboard or receipt summary for the work itself.

Run `render --stage plan|post|review --source /absolute/artifacts/stage.src.html --present`. The CLI renders with bundled `kit/render.mjs`, opens the result through the OS viewer, and records its hashes only after the opener succeeds. It uses `--no-check` to avoid optional browser tooling dependencies; inspect the rendered visual with the host browser when available and fix any layout problems. To present HTML already rendered and inspected with host tools, run `record --stage STAGE --html /absolute/artifacts/page.html --present`. Both commands require an interactive HTML document. A successful viewer command is delivery evidence, not proof the user read or approved it.

Implementation requires `plan` before editing and `post` after editing. A plan remains valid through its implementation; a changed scope requires a new plan. A post or review receipt goes stale when source changes. Plan-only tasks require `plan`; read-only code and PR reviews require `review`. Before creating a PR, run `check --publish` and repair every missing stage. Do not create the PR until it passes. If the current task is not implementation, declare the actual publication scope as implementation and generate its plan and post visuals.

A Stop hook continues once for each unresolved fingerprint, then reports an incomplete workflow. Complete the checkpoint instead of claiming success. If the human explicitly chooses to skip a checkpoint, they can send the exact prompt `visual-review override plan|post|review: reason`. Only the user prompt hook records that exception. Never manufacture that prompt, call the hook with invented human input, or treat receipts as approval.
